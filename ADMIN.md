# Gridika — страница заказов (админка)

План страницы, на которой видно, кто, что и когда купил, и где можно помочь покупателю
(переслать письмо, вернуть деньги, посмотреть код). Здесь только план, кода ещё нет.

---

## 1. Почему нужен свой маленький сервер

Сайт gridika.ru — статический (GitHub Pages): у него нет базы и нет сервера, а значит, ему
негде хранить заказы. Заказы появляются только в момент оплаты, поэтому схема такая:

```
Покупатель → корзина → оплата (ЮKassa / CloudPayments / Т-Банк)
                              │
                              ▼  уведомление об оплате (webhook)
                    Функция «orders» (Yandex Cloud Functions)
                      ├─ проверяет, что платёж настоящий
                      ├─ сохраняет заказ в базу
                      ├─ подписывает ссылку на заказ
                      └─ отправляет письмо с info@gridika.ru (SMTP SpaceWeb)
                              │
                              ▼
                    База заказов (YDB или PostgreSQL в Yandex Cloud)
                              ▲
                              │  чтение по паролю администратора
                    gridika.ru/admin — страница заказов
```

- **Серверная часть живёт в России** (Yandex Cloud): в заказах есть email, это персональные
  данные, по 152-ФЗ их хранят на серверах в РФ.
- **Сайт остаётся статическим.** Страница `/admin` — такая же статическая страница, но все данные
  она получает от функции и только после входа. В самой странице нет ни одного заказа.
- **Стоимость:** при небольшом потоке заказов функции и база укладываются в бесплатный лимит
  Yandex Cloud или стоят десятки рублей в месяц.

## 2. Что хранить о заказе

Таблица `orders`, одна строка — один заказ:

| Поле | Пример | Зачем |
|---|---|---|
| `id` | `GR-7Q4K2D` | номер заказа (в письме, на странице «Спасибо», в коде) |
| `created_at` | 2026-11-12 18:04 | когда оплачен |
| `email` | anna@example.com | куда ушло письмо |
| `items` | список эффектов с настройками | что куплено (то же, что в ссылке на заказ) |
| `codes_count` | 3 | сколько кодов |
| `total` | 3 290 | сколько оплачено, ₽ |
| `discount` | 1 180 | скидка за комплект / пакет |
| `payment_id` | id платежа у провайдера | чтобы найти платёж и сделать возврат |
| `status` | `paid` / `refunded` / `failed` | состояние заказа |
| `email_status` | `sent` / `bounced` / `resent ×2` | дошло ли письмо |
| `order_url` | подписанная ссылка | её можно переслать заново |
| `source` | `utm_source=vk` | откуда пришёл покупатель (если есть метка) |
| `note` | «просил другой цвет» | заметка для себя |

Таблица `events` (журнал): «оплачен», «письмо отправлено», «письмо переслано», «возврат»,
«ссылку открыли». По ней видно, что происходило с заказом и когда.

**Чего не хранить:** номеров карт и платёжных данных (они остаются у платёжного сервиса),
картинок логотипа и фото покупателя (в заказе только сетка кубиков, как сейчас в ссылке).

## 3. Страница `/admin`

### 3.1. Вход
- Вход по паролю администратора → функция выдаёт временный токен (на 12 часов).
- Лучше сразу второй фактор: код из письма на ваш личный адрес или вход через Яндекс ID
  (только для вашего аккаунта).
- Страница закрыта от поисковиков (`noindex`), ссылки на неё нигде на сайте нет.

### 3.2. Сводка сверху
- Выручка: сегодня / 7 дней / месяц, и сравнение с прошлым периодом.
- Заказов и кодов за период, средний чек.
- Самые популярные эффекты (QR, визитка, подарок, логотип, морф, таймер) — столбики.
- Доля заказов: «1 код» / «Комплект» (2–6) / «Пакет» (7+).
- Тревоги: письма, которые не дошли; возвраты; ошибки оплаты.

### 3.3. Список заказов
- Таблица: номер, дата, email, эффекты (цветные метки), кол-во кодов, сумма, статус, письмо.
- Поиск по email и номеру заказа.
- Фильтры: период, эффект, статус, тип заказа (1 код / комплект / пакет).
- Сортировка по дате и сумме; выгрузка в CSV (для учёта в «Мой налог»).

### 3.4. Карточка заказа
- Все эффекты заказа с подписью (как в корзине: «Дерево · zerno-coffee.ru»).
- Кнопки:
  - **Открыть страницу заказа** — то, что видит покупатель (коды, копировать / скачать).
  - **Переслать письмо** — на тот же адрес или на исправленный (если покупатель ошибся в почте).
  - **Открыть в студии** — эффект с настройками покупателя (помочь что-то поменять).
  - **Вернуть деньги** — через API платёжного сервиса, с подтверждением; заказ → `refunded`.
- Журнал событий заказа и заметка.

### 3.5. Покупатели (позже)
- Список email с числом заказов и суммой — видно постоянных клиентов и студии.

## 4. Безопасность

- **Подпись ссылки на заказ — уже сделано.** Страница «Спасибо» показывает код только по ссылке
  `/thanks#order=…&items=…&sig=…` с верной подписью ECDSA (проверка — `verifyOrder` в
  `src/engine/license.ts`, тот же набор открытых ключей, что у ключей). Выдуманная или изменённая
  ссылка кода не открывает. Пока сервера нет, ссылку подписывает `pnpm order sign --file заказ.json`
  (в `apps/fx`); функция `orders` будет делать то же самое после оплаты.
- **Генерация кода на сервере (этап 1).** Сейчас генераторы кода лежат в общем JS сайта, и
  разработчик может вызвать их из консоли браузера. Когда появится функция `orders`, страница
  «Спасибо» будет получать готовый код с сервера по номеру заказа, а генераторы уйдут из сборки сайта.
- **Проверка оплаты.** Заказ создаётся только из уведомления платёжного сервиса после проверки
  его подписи / IP — не из браузера покупателя.
- **Повторные уведомления.** Одно и то же уведомление может прийти дважды — заказ создаётся
  один раз (проверка по `payment_id`).
- **Доступ к данным.** Чтение заказов — только с токеном администратора; токены и пароль SMTP
  хранятся в секретах Yandex Cloud (Lockbox), не в репозитории.
- **Политика конфиденциальности** уже описывает сбор email; при запуске проверить, что в ней
  указаны Yandex Cloud и платёжный сервис как обработчики.

## 5. Этапы

| Этап | Что делаем | Результат |
|---|---|---|
| **0. Решения** | выбрать платёжный сервис (ЮKassa / CloudPayments / Т-Банк), завести Yandex Cloud, включить DKIM на SpaceWeb | понятно, куда приходят деньги и откуда уходят письма |
| **1. Приём заказов** | функция `orders`: webhook → проверка → запись в базу → подписанная ссылка → письмо по шаблону `orderEmail.ts` | покупатель после оплаты получает код без вашего участия |
| **2. Корзина → оплата** | кнопка «Оплатить» в корзине создаёт платёж у провайдера (сумма считается на сервере по `pricing.ts`, а не в браузере) | рабочая покупка от начала до конца |
| **3. Админка MVP** | вход, список заказов, поиск, карточка заказа, «переслать письмо» | видно, кто что купил; можно помочь покупателю |
| **4. Сводка и деньги** | графики выручки и эффектов, возвраты из админки, выгрузка CSV | учёт и решения по ценам |
| **5. Удобства** | уведомление о каждом заказе в Telegram, покупатели, UTM-метки, заметки | меньше ручной работы |

Этапы 1–3 — минимум для запуска продаж. Каждый этап выкатывается через `dev` → проверка →
`main`, как описано в `RELEASE.md`; функции и база деплоятся отдельно от сайта, поэтому их
обновление сайт не роняет.

## 6. Что нужно от вас перед началом

1. Какой платёжный сервис (от этого зависят webhook и возвраты). Для самозанятого чаще всего
   ЮKassa или CloudPayments — оба умеют отправлять чек в «Мой налог».
2. Аккаунт Yandex Cloud (платёжный аккаунт, можно на бесплатном лимите).
3. Пароль приложения для `info@gridika.ru` (SMTP SpaceWeb) и включённый DKIM.
4. Нужен ли Telegram-бот с уведомлением о каждом заказе.
